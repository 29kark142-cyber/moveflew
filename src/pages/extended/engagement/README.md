# Engagement frontend

## Exports and parent route wiring

`client/src/pages/extended/EngagementPages.tsx` exports these authenticated workspace modules. Each accepts `ModuleProps` from `shared/expansion.ts`:

| Export | Suggested authenticated route |
| --- | --- |
| `PipelinePage` | `/app/pipeline` |
| `CommunicationsPage` | `/app/communications` |
| `ReportsPage` | `/app/reports` |
| `MarketingPage` | `/app/marketing` |
| `ReviewsPage` | `/app/reviews` |
| `IntegrationsPage` | `/app/integrations` |
| `InventoryCatalogPage` | `/app/inventory-catalog` |

Public Wouter route components are default exports and require the Wouter route prop shape `{ params: { token: string } }`:

| Component | Required public route |
| --- | --- |
| `QuoteWidget.tsx` | `/quote/:token` |
| `CustomerPortal.tsx` | `/portal/:token` |
| `ReviewFeedback.tsx` | `/review/:token` |

The public pages intentionally use only their token-scoped `/engage/public/*` endpoints. They do not use CRM login or workspace authentication.

## API contract used

`client/src/lib/engage-api.ts` uses `crmFetch`, which prefixes `/api/crm`, carries workspace/auth context for authenticated requests, and uses the public-request flag for token routes and `/engage/api-docs`.

The frontend expects the REST paths and response fields documented in `expansion-contract.md`:

- Customer stage moves call the existing `crm.updateCustomer(id, {status})`; lead details write consent, tags, assignment, and UTM metadata through `/engage/customer-preferences/:id`.
- Communication creation is always a record request. Outbound email/SMS is visibly described as a blocked draft; this UI never claims delivery.
- Reports render only values returned by `/engage/reports`; record-level CSV export remains disabled when the API did not return its optional filtered `records` collection. CSV cells are formula-neutralized.
- Campaigns, reviews, catalog items, keys, webhooks, webhook delivery history, integrations, and docs call their corresponding `/engage/*` endpoints.
- New access-key tokens and webhook secrets remain React state only and are displayed only once. They are never written to `localStorage`, session storage, or console logs.
- A widget or portal one-time token yields `/quote/:token` or `/portal/:token` and widget iframe code using `window.location.origin`.
- Portal inventory is submitted for staff review only. Proposal links use job data returned by that token. Portal checkout calls `POST /engage/public/portal/:token/invoices/:id/checkout` with the outstanding integer-cent balance when at least 50 cents, opens the returned **TEST** checkout in a new tab, and never marks an invoice paid locally. `?pending=payment` causes the portal to refresh while awaiting webhook-verified payment status.

## Boundaries

- Parent code owns app navigation, Wouter route mounting, backend route implementation, schema/migrations, Russian catalog generation, and incorporation of tenant catalog items into existing inventory pickers.
- No fake provider connection, social-review publication, Google/Xero sync, outbound email/SMS delivery, payment confirmation, customer identity, seed customer data, or estimated price is generated by these pages.
- The integration registry is rendered exactly from its API response. API/CSV/documentation availability should remain distinct from a connected provider on the backend.
- Server authorization and tenant relationship checks remain authoritative. Client controls are only an additional role-aware UX layer.
